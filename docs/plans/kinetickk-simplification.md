# План упрощения KINETICKK

Статус: предложение; изменения реализации не начаты. Связанный документ — [изменение Pokeball](pokeball-simplification.md).

Этот план применяет независимые изменения архитектуры к KINETICKK. Сейчас приложение проверяется относительно Core `de9ef7384795680c836d5e6c2c9b394286058670`; выбор новой версии, обновление pin и миграция проектных проверок относятся к этому плану.

Цель — устранить пять наблюдаемых проблем: повторение механики принятия, сложность локальных команд, зависимость API от имён потребителей, хрупкие проверки исходного текста и ручные режимы копирования Gameplay.

Сохранить владельцев Content/Profile/GameplayRun/Session и поведение игры. Физическое объединение Gradle-модулей не является целью: оно само по себе не решает перечисленные проблемы. Работа начинается на текущем коде с незакоммиченными изменениями, поэтому перед реализацией нужно зафиксировать отдельный исходный снимок, не очищая рабочее дерево пользователя.

## 1. Зафиксировать поведение и стоимость на существующих сценариях

Использовать существующие тесты GameComponent, DefaultProfileComponent, DefaultAppSessionComponent, Nucleus, изоляции Gameplay и проекций.

Опорные сценарии: старт; mute при активном забеге; изменение громкости; открытие/закрытие настроек; выход с принятым и отклонённым прогрессом; ошибка сохранения; ошибка после доставки результата; замена завершённого забега.

Запустить существующий performance harness для idle/paused, pointer, обычного и насыщенного игрового кадра, а также создания состояния. Сохранить время и аллокации в штатный каталог результатов. Отдельный framework измерений не нужен.

55 компонентных тестов проходили во время предыдущего разбора, но рабочее дерево после этого менялось. Для исходного снимка нужны свежие результаты.

## 2. Отвязать проверки от написания исходников

Начать с `build-logic/.../pokeball/PokeballModel.kt`, `PokeballResolver.kt` и `ProtocolShapeVerifier.kt`.

- Заменить проверки литеральных фрагментов функций тестами проверяемого поведения и ограничений. Например, для Arc Coil оставить максимум шести целей и поведение седьмой.
- Сохранить контроль запрещённых зависимостей, циклов, доступа к чужому состоянию и платформенных границ. Использовать уже доступную структурную проверку и ограничения модулей; не строить новый Kotlin-парсер ради старой схемы.
- На время старого Core сохранить нужные ему семантические проверки команд. Убирать их совместно с обновлением контракта, а не отключением gate.
- Сделать runtime wiring источником маршрутов. Нужные отчёты/manifest формировать как производный результат. Документы оставляют решения о поведении, но перестают вручную дублировать весь реестр связей и точные числа маршрутов.

Проверка: переименование локальной переменной, извлечение чистого helper и добавление нового допустимого маршрута не требуют правок строковых ожиданий проверяющего кода. Реальное превышение лимита и запрещённая зависимость по-прежнему обнаруживаются. Изменённые проверки проходят собственные отрицательные сценарии.

## 3. Собрать общую механику принятия из существующих реализаций

Из DefaultProfileComponent, GameComponent и DefaultAppSessionComponent выделить один небольшой механизм для текущего Inline-исполнения:

- сериализация входов конкретного владельца;
- preflight и публикация состояния вместе с доступностью всего output batch;
- выполнение outputs после принятия;
- сериализованная обработка завершений;
- завершение принятой работы перед пробросом первой отложенной ошибки.

Владельцам оставить их State, decide/read, доменные ошибки, проверку собственных границ и обработчики эффектов. Публикация Gameplay включает согласованный render snapshot; чтение контекста выполняется для текущего входа.

Обобщать только реально совпавшие части трёх реализаций. Не добавлять поддержку других исполнителей, durable outbox, reflection, event bus или coroutine actor. Начать с Profile и Session; Gameplay подключить после сохранения его поведения и измерений.

Проверка: новая простая фича использует существующее принятие, а не копирует dispatch/drain loop. Общие ordering/fault-тесты проверяют один механизм; компонентные тесты продолжают проверять правильность его подключения. Это не означает удаления существующих регрессий.

## 4. Перейти на компактные команды после изменения Core

Обновить явную привязку Core и проектные правила по связанному плану. Реальные архитектурные изменения, несовместимые со старым pin, начинать после этого перехода.

Первым вертикальным сценарием взять mute:

`Session принимает намерение → исполнитель вызывает Profile → Profile принимает изменение → Session обрабатывает результат → активный Gameplay принимает настройки → Session завершает workflow`.

- Убрать ручные transport envelopes, protocol-identity enums, issuer enums и causalScope/depth там, где их полностью заменяет закрытый синхронный вызов.
- Сделать связь завершения с текущим вызовом обязанностью общего механизма. Бизнес-решения по результату по-прежнему принимает источник.
- Сохранить различие отказа до принятия и ошибки после принятия. Ошибка сохранения не превращает изменённый профиль в неизменённый.
- Перенести из pending State только технические поля корреляции. Фазы workflow и значения, нужные следующему бизнес-решению, остаются в Session.
- После mute переносить по одному: выбор формы, старт/пауза, применение настроек, rebirth, выход и передачу прогресса.

ProfileRevision для сохранения/чтений и RunId для жизни забега сохраняют самостоятельный смысл. Их нельзя удалить вместе с лишними транспортными полями.

Проверка каждого шага: обычное завершение, отказ участника, ошибка после принятия, недопустимое повторное завершение, сохранение порядка и исходного контекста. Сценарии, которые старая реализация проверяла через токены, заменить проверкой эквивалентного свойства нового механизма.

## 5. Отвязать Profile API от списка потребителей

Вместо `ProfileCommandSource.LocalSession/GameplayRun`, `SESSION_*` и `acceptFromSession/acceptFromGameplay` выдавать существующему объекту Profile узкие интерфейсы по возможностям: чтения, настройки, применение прогресса. Точные имена выбрать при изменении API; отдельный proxy на каждый метод не нужен.

Assembly передаёт нужное представление потребителю. Profile продолжает владеть бизнес-политикой, схемами результатов и сохранением. Обязательная бизнес-проверка прав, если она появится, не заменяется фактом наличия ссылки.

После миграции всех вызовов удалить ручной ProfileModuleResultRouter и устаревшие source/issuer/protocol types вместе с их уже заменёнными проверками.

Проверка: дополнительный тестовый потребитель использует существующую операцию через реальный binding. Для его подключения меняется композиция, но не перечень известных вызывающих в Profile и не его доменная логика.

## 6. Упростить модель кандидата Gameplay

Привести состояние внутри того же GameplayRun к явным частям: управляющий ввод, конфигурация/билд и мир симуляции. Они не становятся самостоятельными владельцами или сервисами.

- Управляющий ввод и настройки — immutable значения. Pointer/brake/viewport обновляют их, не требуя специальной копии всего MutableGameState.
- Хранимое состояние мира и его вложенные значения должны иметь один понятный способ получения изолированного кандидата. Предпочесть data class/value-представления с неизменяемыми вложенными значениями; изменяемые builders допустимы только внутри кандидата и не доступны читателям.
- Массивы и mutable-сущности перевести последовательно по группам, сохраняя правила RNG, порядок элементов, nullable-полей и pending outputs. Механические оптимизации хранилищ сосредоточить в самих хранилищах.
- Удалить `shareStableReductionStorage`, `copyForScalarInputReduction` и список `preservesStableSimulationStorage`, когда структурное разделение состояния делает их ненужными.
- Удалить специальное знание о `DashRequested` из binding. Проекция получает основания для переиспользования из неизменяемых частей состояния; при сомнении строится заново.
- Нужные доменные поля прежнего GameplayState и render model сохраняют смысл. Согласованная публикация State/render snapshot остаётся одной операцией.

Целевой результат: новое обычное поле состояния добавляется в своё value-представление и бизнес-логику, без регистрации в отдельном списке режимов безопасного копирования. Новое mutable-хранилище всё ещё требует проверки изоляции — архитектура не может отменить семантику aliasing.

Проверка: полный старый snapshot не меняется после следующего перехода; отклонение оставляет исходное состояние; одинаковые seed/inputs дают одинаковый результат; оптимизированная проекция совпадает с независимой свежей. Повторить исходные performance-сценарии. Если появляется устойчивая регрессия времени или аллокаций, оптимизировать конкретное хранилище; не объявлять шаг завершённым по одному лишь уменьшению кода.

## 7. Удалить заменённые механизмы и проверить всё вместе

Удалять прежние routes, wrappers, циклы dispatch и проверки формы только после переноса их поведения. Не оставлять постоянный параллельный путь старого и нового исполнения.

Запустить соответствующие desktop-тесты, build-logic-тесты, проверки зависимостей и обновлённой архитектуры. Затем проверить Android-сборку, Wasm-компиляцию и пользовательские сценарии на Desktop/Web; для устройства повторить доступные регрессии ввода/звука. Формальный conformance выполнять на чистом снимке и новой версии Core.

Повторить три упражнения из плана Pokeball. Завершение означает: один механизм принятия, компактные локальные команды, независимый от списка потребителей API, проверки свойств вместо точных строк, один понятный путь изоляции состояния. При этом сохранены наблюдаемое поведение и проверенные характеристики исполнения.

## Порядок изменений

1. Исходный снимок и измерения → проверки исходников → общий механизм принятия.
2. Получить согласованную новую версию Core. Использовать mute как проектный сценарий проверки её применимости.
3. Новый Core/pin → mute → остальные команды → отвязка API и удаление старой маршрутизации.
4. Модель Gameplay → итоговые функциональные и performance-проверки → три упражнения на расширение.

Каждый этап оставляет одну работающую реализацию своего перенесённого сценария и ограниченный проверяемый diff. Публикация изменений выполняется только по отдельному запросу.

# План изменения Pokeball: меньше обязательной механики

Статус: предложение семантических изменений; действующий Core этим документом не изменён.

Цель — сделать обычную локальную композицию такой же понятной, как изменение внутри одного Ball. Менять существующие положения и примеры; не вводить Pokeball Lite, новые профили, законы, обязательные документы или собственный DSL.

Исходная версия для предложенных изменений — Pokeball `3ad7eb8799d1860296ca177e7c959a616fa68db8`. Область плана — законы Core, их определения, учебные примеры и производные инструкции. Примеры ниже самостоятельны и не задают обязательные имена типов или устройство проекта.

## 1. Убрать сам факт пересечения Ball из обязательных причин создания идентификаторов

Сейчас PBA-15, §3.5 включает `crosses a Ball boundary` в причины наличия стабильного SemanticHandle. §6.9 требует канонические command/result tuples; для устранения оболочек нужно доказывать тождество полному tuple.

Изменение:

- Удалить `cross-Ball` как самостоятельный триггер стабильного handle. Уточнить существующий `retained`: хранение промежуточного значения только на время текущего вызова само по себе также не требует handle. Сохранить идентичность там, где результат может прийти позднее, переупорядочиться, повториться, пережить восстановление или наблюдаться независимо от текущего вызова.
- В §§6.9/6.13 описать синхронный типизированный вызов и его возврат как достаточное представление связи запроса с результатом. Полные envelopes оставить для путей, которым действительно нужна переносимая причинная информация.
- Убрать необходимость восстанавливать отсутствующие tuple-поля только ради доказательства эквивалентности материализованной записи. Для обычного вызова проверять фактический порядок принятия, целевого владельца и возврата.

Пример короткой замены нормативного текста, который затем нужно согласовать во всех затронутых положениях:

> An immediate same-build call may use its typed target and call scope as command identity and provenance. Crossing a Ball boundary alone does not require a materialized handle, source token, result token, or protocol identifier.

Пример применения: `CounterCommands.increment(): IncrementResult`, где результат — `Changed(value)` или `NotAccepted(reason)`. Счётчик принимает собственное изменение; источник получает результат через свой сериализованный обработчик. Синхронный вызов выполняется исполнителем уже принятого output, а не внутри чистого `decide`. Для связи непосредственного возврата с этим вызовом отдельные command/result tokens не нужны.

Ошибку после принятия нельзя представить как `NotAccepted`. Неизвестный исход внешнего действия сохраняет свой смысл. Эти различия выражаются нужными конкретному контракту типами, без обязательной одинаковой формы carrier во всех реализациях.

## 2. Ослабить протоколизированное доказательство происхождения для статически связанных локальных вызовов

В §§6.9, 10.2 и 10.7 заменить требование отдельных полей происхождения для такого вызова ссылкой на уже существующую доверенную границу и доступный вызывающему интерфейс. Для недоверенных и независимо доставляемых сообщений сохранить настоящую проверку источника.

В учебном примере показать одного владельца Counter и два ограниченных представления его возможностей: чтение значения и увеличение счётчика. Потребители получают подходящий интерфейс через Assembly. API счётчика описывает его операции; имена потребителей остаются в композиции. Если бизнес-политика зависит от вызывающего, её проверка остаётся у владельца.

Проверка примера: дополнительный разрешённый потребитель уже существующей операции подключается через wiring. Его появление не меняет тип результата, доменную логику или перечень имён вызывающих в Counter.

Это частично исправление примера и способа применения: нынешний Core не требует именно enum с именами потребителей. Не создавать новый закон, запрещающий такие enum.

## 3. Убрать обязательные числовые ограничения на форму статически конечной композиции

Пересмотреть PBA-29/§10.9 и связанные положения PBA-38/§8.3, §8.4, §8.7:

- Убрать обязательные `maxDeclaredDependenciesPerBall`, `maxFlowParticipants`, `maxRoutesPerFlow` как критерии корректности обычной статической композиции. В примерах они могут оставаться проектными ограничениями, когда у них есть конкретный смысл.
- Для статически конечного синхронного workflow убрать обязательное протаскивание causalScope/depth и схему передачи level-1/level-2 reservations. Конечная структура исполнения может сама закрывать этот вопрос.
- Не требовать отдельно вычислять общий геометрический fan-out для цепочки, полный объём работы которой уже ограничен её структурой.
- Сохранить реальные ограничения очередей, внешних запросов, сохраняемых outputs и иной растущей работы. При фактической возможности переполнения нельзя принять работу, которую механизм затем потеряет.

Пример: источник один раз выдаёт `Counter.increment`, счётчик возвращает результат, источник принимает его и завершает обработку. В такой закрытой цепочке числовой бюджет в каждом сообщении не добавляет ограничения к уже конечному исполнению. Одного DAG импортов для этого вывода недостаточно: повторная выдача команды из обработчика результата всё ещё может создать бесконечную цепочку.

Добавление статического потребителя не требует пересматривать обязательный глобальный лимит числа связей. Реальные связи остаются видимыми из типов и wiring; динамически растущая работа сохраняет свои ограничения.

## 4. Сократить требования к доказательствам до свойств механизма

В §§14/17 и существующих производных инструкциях заменить предписания конкретных полей и carrier-конструкций там, где предыдущие шаги разрешают обычный вызов. Удалить связанные обязательные проверки формы.

Сам нынешний Core уже позволяет контракт в исходном коде и переиспользование проверок binding. Для этого не нужен новый закон. Показать это на существующем примере: тип операции и wiring — исходные сведения; manifest и таблица маршрутов при необходимости получаются из них.

Контрольный пример — переименование локальной переменной или извлечение функции проверки лимита в реализации Counter. Увеличение до разрешённой границы и отказ за ней сохраняют поведение. Проверки этих свойств продолжают работать без привязки к точному тексту функции.

Также заменить многословный пример binding на один небольшой вариант сериализованного принятия и обработки outputs. Он должен показывать повторное использование механики двумя владельцами, а не требовать от каждого автора её переписывания. Пример не становится обязательной библиотекой.

## 5. Для состояния ослабить требования к представлению, где они реально мешают, сохранив смысл изоляции

Проверить §§3.3, 7, 8.5/8.8 и связанные примеры на предписание физических копий. Заменить такие предписания, если они есть, требованием наблюдаемой изоляции: чтения видят принятые значения; отклонённый кандидат их не меняет.

Core уже допускает разные физические представления accepted frame. Не добавлять ещё одно исключение, если существующего разрешения достаточно.

Практический пример: один Document Ball хранит immutable `DocumentState(metadata, paragraphs)`. Изменение заголовка создаёт новые metadata и разделяет неизменные paragraphs. Изменяемый builder текста принадлежит только текущему кандидату и не выходит к читателям. Части структуры не требуют отдельных Balls.

Проверка примера: изменение кандидата не меняет ранее опубликованный документ; отказ сохраняет прежнее состояние. Конкретный способ хранения и копирования остаётся выбором реализации. Если эти возможности уже разрешены Core, достаточно сократить предписывающий пример и производные инструкции.

## 6. Свести изменения в одну согласованную версию

1. Редактировать положения в их существующих источниках. Синхронизировать затронутые PBA-проекции, определения, примеры и проверки; не добавлять второй набор законов.
2. Заменить существующий пример локальной композиции компактным примером Counter. Показать нормальный результат, отказ до принятия и ошибку исполнителя после принятия.
3. Сократить поддерживаемые skills по новым формулировкам. Обновить их поддерживаемый источник вместе с производными инструкциями.
4. Проверить согласованность Core, его производных материалов и skills штатными инструментами. Проверки устаревших обязательных оболочек заменить проверками сохраняемых свойств.
5. Описать семантические изменения в существующих материалах версии: какие обязательства сняты, при каких обстоятельствах идентичность и ограничения по-прежнему нужны. Подготовить согласованный выпуск Core и производных материалов.

## Проверка результата

На самостоятельном учебном примере выполнить три изменения: добавить небольшой Ball в существующий binding, подключить дополнительного потребителя операции, безопасно переименовать переменную или извлечь функцию. Учитывать доменный код, повторённую механику и вручную синхронизируемые описания отдельно.

Успешный результат: изменения обходятся без новых token/carrier/issuer типов для обычного локального вызова, без ещё одного диспетчера и без ручного редактирования производных таблиц. Сценарии принятия, отказов и порядка выполнения сохраняют ожидаемое поведение. Для Document отдельно проверяется изоляция состояния. Результаты подтверждают применимость упрощённой формы на этих примерах; они не объявляются доказательством удобства для всех систем.

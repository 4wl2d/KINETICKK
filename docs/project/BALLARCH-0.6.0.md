# Ballarch и KINETICKK 0.6.0

Оценка и локальное применение от 30 октября 2026 года.
Исходная версия игры: `b1a5faf52806e665c456c08f4bcab6ae49c5e8f1`.
Источник архитектуры зафиксирован на
[`e216e21d`](https://github.com/4wl2d/Ballarch/tree/e216e21d91617ce751a90c9968c293c126382759):
[Core 2.0.0-rc.1](https://github.com/4wl2d/Ballarch/blob/e216e21d91617ce751a90c9968c293c126382759/spec/ballarch-core-2.0.md),
[переход с 1.5](https://github.com/4wl2d/Ballarch/blob/e216e21d91617ce751a90c9968c293c126382759/docs/migration-from-1.5.md).

## Вывод и границы применения

Ballarch полезен для KINETICKK как способ отделять решение от исполнения эффекта,
различать подтверждённый и неопределённый исход и проверять границы модулей.
Наиболее подходящий участок — сохранение профиля. Физика, генерация мира,
отрисовка и локальное состояние экранов не требуют общего протокола внешних
эффектов: Core §1 прямо оставляет такие вычисления обычным кодом.

В 0.6.0 выборочно применены эти принципы. Полный Ballarch runtime не подключён,
соответствие Core 2.0 не заявляется. Это существенная граница результата:
одних названий `ball`, `nucleus` и `flow` для соответствия недостаточно.
Kotlin reference рассчитан на JVM; проекту с Android, Desktop и Wasm понадобились
бы перенос runtime, собственные адаптеры и полные проверки его протокола.
Для локального сохранения и синхронных игровых взаимодействий такая миграция
сейчас не имеет доказанного преимущества перед существующей реализацией.

В исходной версии уже были чистые решения, единственный владелец состояния,
фиксация до исполнения, ограниченная очередь завершений, типизированные ответы,
защита от повторного входа и отдельный `OutcomeUnknown`. Их нельзя записывать
в улучшения этой работы. Новые проверки также не доказывают, что раньше
пользователь терял сохранения: такой дефект здесь не воспроизводился.

## Что изменено

1. В Profile разделены `decide` для запросов и `complete` для результата записи.
   `complete` возвращает готовый `ProfileAcceptedFrame`, без варианта отказа.
   Завершение больше не является запросом `ProfileNucleusPulse`; убраны две
   временные обёртки на пути завершения и недостижимая ветка отказа в owner.
   [Decider](../../ball/profile/nucleus/src/commonMain/kotlin/kinetickk/ball/profile/nucleus/ProfileNucleus.kt),
   [owner](../../ball/profile/impl/src/commonMain/kotlin/kinetickk/ball/profile/impl/DefaultProfileComponent.kt).
2. Сохранены идентификатор эффекта, проверка ревизии, порядок публикации и
   выполнения, ограниченная очередь, исходы записи и реакция на программные
   ошибки. Неверное или повторное доверенное завершение остаётся ошибкой;
   оно не может завершить более новую запись. Это синхронный внутренний
   контракт, а не новый асинхронный `CallRef` runtime.
3. `verifyArchitecture` теперь запрещает production-зависимости `api` и
   `nucleus` на закрытые реализации, UI и resource-модули. Разрешены публичные
   `:api` и `:foundation:common`; тестовые зависимости для fixture сохранены.
4. Добавлена проверка импортов всех рабочих `nucleus/src/*/kotlin` (кроме
   `*Test`) на UI, платформенное I/O, корутины, reflection и источники
   внешнего времени.
   Отрицательные примеры покрывают 36 запрещённых рёбер и 13 вариантов импортов.
   Это **проверка импортов**, а не доказательство чистоты: полностью
   квалифицированные обращения, default imports и эффекты внутри разрешённых
   helper-функций требуют ревью и поведенческих тестов.
5. Добавлены проверки всех исходов завершения, старых/повторных/неверных
   завершений и семи сценариев поведения хранилища. Отдельно проверяется,
   что значение в кеше после неподтверждённого flush не превращает `Unknown`
   в успешное сохранение. Нет слепой повторной записи.

Новые fault-тесты расширяют доказательства уже существовавшего поведения
адаптера. Они не заменяют conformance scenarios и crash exploration Core.
Формат профиля, ключи хранилищ, баланс, версия и интерфейс игры не изменены.
README проверен: описание 0.6.0 остаётся актуальным, правка не понадобилась.

## Карта эффектов и оставшиеся ограничения

| Участок | Оценка по Ballarch | Что действует в KINETICKK |
|---|---|---|
| Физика, мир, проекции, UI | Обычные вычисления и локальное состояние | Существующий детерминированный игровой цикл |
| Чтение профиля | Safe по контракту чтения содержимого | Ошибка чтения не означает мутацию |
| Запись снимка | Консервативно NonIdempotent: провайдер не дедуплицирует runtime-ключи | Один синхронный вызов; `Written`, отказ до записи или `OutcomeUnknown` |
| Звук, настройки дисплея | Побочные эффекты вне decider | Прежние адаптеры; без гарантий Core |
| Session → Profile / Gameplay | Взаимодействия владельцев | Прежние inline-вызовы с подтверждённым ответом либо ошибкой |

Это аналитическая классификация, не новые зарегистрированные runtime-порты.
Повтор `set(snapshot)` не становится Ballarch Idempotent только потому,
что два одинаковых значения совпадают: по спецификации нужна дедупликация
по переданному runtime ключу. Ключи и окна дедупликации здесь не добавлены.

Сохранение предполагает честные ответы конкретного платформенного провайдера.
Успех после readback по-прежнему требует успешного ответа записи; совпадение
кешированного значения само по себе не доказывает долговечность. Ни новая
структура, ни тестовый fake не гарантируют сохранность при отказе устройства.

Нет durable outbox/ledger, общего механизма deadlines, восстановления
незавершённых обязательств, fencing между двумя процессами и exactly-once
внешних эффектов. После программной ошибки прежнее pending-состояние может
требовать перезапуска. Следующее обычное изменение профиля может сохранить
новый полный снимок; новая автоматическая retry/reconciliation политика не
вводилась. Полный Durable runtime имел бы смысл заново оценить при появлении
облачного sync, покупок или внешнего сервиса с операциями, переживающими процесс.

## Измерения до и после

Одинаковый [измерительный тест](../../ball/profile/impl/src/desktopTest/kotlin/kinetickk/ball/profile/impl/ProfileOwnerPerformanceBenchmarkTest.kt)
скопирован в отдельную исходную checkout и в candidate. SHA-256 fixture:
`528da5bd86ef9f3f68faf1e29bb4687f020850439ee7594cd3926ddb2de68443`.
На момент замеров исходная checkout отличалась от базового коммита только этим тестом;
candidate включал изменения. Обе честно отмечены как dirty.

Порядок отдельных JVM: A1 → B1 → B2 → A2. В каждой: 5 прогревочных и
10 измерительных интервалов по 180 мс на сценарий. Один хост macOS/arm64,
OpenJDK 25.0.4.1, одинаковая конфигурация Gradle Test. Сборки и другие тесты
во время измерений не запускались. Каждый вызов проходит настоящий owner,
типизированный ответ и completion. Вне таймера проверяются число записей,
ответы, значения preferences, ревизии и статус сохранения.

В таблице — среднее двух медиан отдельных JVM. Это небольшой локальный
микробенчмарк, не оценка статистической значимости.

| Сценарий / метрика | До | После | Изменение |
|---|---:|---:|---:|
| Owner + fake resource, нс/вызов | 180,61 | 180,73 | +0,07% |
| Owner + fake resource, выделено байт/вызов | 736 | 712 | −3,26% |
| Owner + codec + readback в памяти, нс/вызов | 2 897,09 | 2 712,89 | −6,36% |
| Owner + codec + readback в памяти, выделено байт/вызов | 4 120 | 4 044 | −1,84% |

Время owner по JVM: до 183,34 / 177,87 нс, после 180,45 / 181,01 нс.
Это практически одинаковая скорость. Для codec разброс заметнее:
до 2 940,14 / 2 854,04 нс, после 2 864,66 / 2 561,11 нс.
По двум процессам нельзя уверенно приписать разницу в 6,36% архитектуре.
JIT и escape analysis также меняют allocations: owner до выделял 744 / 728
байт, после 712 / 712. Измеренный выигрыш 16–32 байта согласуется с удалением
обёрток, но не является переносимой гарантией размера объектов на любой JVM.

Здесь измерены выделения текущего потока, **не общий RSS/heap игры**.
Codec работает со строкой в памяти, без Preferences, диска или Android
SharedPreferences. FPS, frame time, GPU, энергопотребление и время реальной
записи этим тестом не измеряются. Оснований обещать их улучшение нет.

| Структурная метрика | До | После |
|---|---:|---:|
| Leaf-модули / объявленные зависимости | 23 / 84 | 23 / 84 |
| Production Kotlin: файлов / физических строк | 438 / 136 755 | 438 / 136 755 |
| Build-logic `.kt`: файлов / строк | 9 / 1 075 | 10 / 1 174 |
| Kotlin тесты приложения: файлов / строк | 513 / 142 911 | 516 / 143 359 |
| Build-logic тесты: файлов / строк | 5 / 504 | 6 / 611 |
| Два изменённых desktop JAR, байт вместе | 111 447 | 110 506 |
| Классы в этих двух JAR | 50 | 49 |

Строки включают комментарии и пробелы; `.kts` не включены в Kotlin-таблицу
(в convention plugin ещё +10 строк). Уменьшение двух JAR на 941 байт
не означает такое же уменьшение APK или Web bundle. Внешние зависимости
и число модулей не выросли. Основная добавленная стоимость сопровождения —
проверки, измерительный тест и эта документация.

## Сравнение по критериям

| Критерий | Объективная оценка результата |
|---|---|
| Разделение запросов и завершений | Лучше: невозможность отказа завершению выражена типом результата; меньше промежуточных объектов |
| Архитектурные границы | Лучше: новые запрещённые рёбра и импорты ловятся существующей CI-задачей |
| Корректность сохранения | Сохранена; новых эксплуатационных гарантий нет, расширена проверка неопределённых исходов |
| Корреляция и повторные ответы | Сохранены; добавлены прямые тесты старого ответа при новой записи |
| Тестируемость | Чистый `complete` проще вызывать отдельно; до изменения логика уже была чистой и тестируемой |
| Объём production-кода | Практически без изменения; дополнительный код сосредоточен в проверках |
| Когнитивная сложность | Локально меньше смешения запросов и результатов; дополнительный sensor требует сопровождения |
| Аллокации | Небольшое локальное уменьшение подтверждено JVM-пробой; влияние на общий heap не измерено |
| Время выполнения | Убедительного выигрыша не установлено; owner практически без изменений |
| FPS, лаги, GPU, батарея | Не измерены; физика и отрисовка не менялись |
| Размер приложения | Два JAR немного меньше; сравнительных APK/Web bundle измерений нет |
| Скорость сборки | Сопоставимый холодный/инкрементальный эксперимент не проводился; sensor добавляет чтение исходников |
| Конкурентность | Прежний один writer и inline scheduling; новые потоки/очереди/параллелизм не добавлены |
| Масштабирование | Не улучшено; для локальной игры это не цель изменения |
| Crash recovery и долговечность | Прежние платформенные сохранения; нет нового durable runtime или recovery ledger |
| Совместимость данных | Схема, ключи и public capabilities прежние; codec/storage и интеграционные тесты прошли |
| Кроссплатформенность | Общие тесты прошли на JVM и Wasm; Android debug собран. Физический Android не проверен |
| Безопасность | Новых security-гарантий нет; sensor не является изоляцией или security scanner |
| UX и игровые возможности | Не изменены; не исправлялись сообщения интерфейса и баланс |
| Независимость от библиотеки | Новый runtime/dependency не нужен; изменения остаются обычным KMP-кодом |
| Полное соответствие Ballarch | Нет: внедрены отдельные принципы, conformance Core 2.0 не проходился |
| Зрелость подхода | Исследована версия 2.0.0-rc.1; перенос всего проекта повысил бы зависимость от ещё меняющейся спецификации |

Итоговая оценка: небольшое положительное изменение в ясности контракта,
контроле границ и локальных аллокациях. Оно не превращает игру в более быструю
или более надёжную при сбое питания. Массовая миграция на полный runtime
добавила бы механизмов и, для Durable, как минимум три durable-записи на
вызов с побочным эффектом по Core §10; текущие измерения не дают оснований платить
эту цену во всём игровом цикле.

## Проверка и воспроизведение

Прошли локально:

- 365 JUnit-результатов: build-logic, Profile nucleus/impl/resource, Session
  nucleus/impl, foundation/common, app/shared. В этот счёт входит один
  opt-in benchmark test, который при обычном запуске возвращается без замеров;
  реальные четыре измерительных запуска выполнены отдельно.
- 155 browser-тестов Profile на Wasm в headless Chromium.
- `:app:android:assembleDebug` и `:app:web:compileKotlinWasmJs`.
- `verifyArchitecture` в обычном и isolated-projects режиме,
  включая отрицательные fixture новых правил.

Отдельно на исходном production-коде выполнены 159 JUnit-результатов трёх
модулей Profile, включая ту же новую матрицу семи исходов хранилища: всё
прошло. Это подтверждает, что обработка неопределённой записи уже работала
до изменения; здесь улучшены её проверка и форма контракта.

Первый локальный запуск остановился из-за internal codec import в новом
benchmark fixture. Он исправлен до замеров; последующие проверки успешны.
Не выполнялись полный набор 13 balance shards, ручной playtest, тесты на
физическом Android, Windows/Linux, GitHub CI, full Ballarch conformance и
имитация аварийного завершения процесса/отказа устройства. Симуляция и
рендер не менялись, поэтому баланс и FPS не объявляются повторно проверенными.

Команды для затронутых контрактов:

```sh
./gradlew :build-logic:test verifyArchitecture \
  :ball:profile:nucleus:desktopTest :ball:profile:impl:desktopTest \
  :ball:profile:resource:desktopTest :flow:session:nucleus:desktopTest \
  :flow:session:impl:desktopTest :foundation:common:desktopTest :app:shared:desktopTest
./gradlew verifyArchitecture -Pkinetickk.gradle.isolatedProfile=true --isolated-projects
CHROME_BIN=/path/to/chromium ./gradlew -Pkinetickk.variant=debug \
  :ball:profile:nucleus:wasmJsBrowserTest :ball:profile:impl:wasmJsBrowserTest \
  :ball:profile:resource:wasmJsBrowserTest :app:web:compileKotlinWasmJs \
  :app:android:assembleDebug
```

Для измерений см. [performance tools](../../tools/performance/README.md).
